## 一、执行原则与阶段安排

1. 正确性变更与性能变更分开交付，每批只有一个主要目标。
2. 比较旧代码时保存工作区差异和文件摘要，不能只记录 HEAD，因为工作区已有用户未提交修改；不得回滚、覆盖或混入无关修改。
3. 每次运行记录代码、模型、特征提取方式、数值精度、完整参数、硬件/运行环境与缓存状态。
4. 使用测试副本和隔离缓存；基准运行不移动、删除或隔离原始媒体。
5. 正式收益验证遵循 preregistering-analysis：先在开发素材上确认可运行，再冻结指标、对照配置、样本、重复次数和判据；正式评估集不用于调参。现有反例及调试结果继续标为探索性。
6. 每批先通过回归，再看三维指标；未通过的实验保持非默认或撤回该批变更，不降低验收标准来宣布通过。
7. GPU 环境缺失不阻塞 CPU 正确性工作，但 GPU 相关收益和支持范围保持“未验证”，不能用 CPU 结果替代。
8. 本文不是已经冻结的统计预注册，也不承诺加速倍数；正式实验按批次另存不可事后修改的验证协议。

## 二、逐批实施清单

### B01：建立可复现基线，把已知问题纳入回归

**改动范围**：识别测试、基准入口、测试数据清单；不改生产算法。

- [ ] 将上一轮临时诊断转为正式、可单独运行的行为回归：多条有效轨迹、重复源帧证据、等时长不同采样密度、尾窗口、前后端标签、FAISS 预算覆盖。
- [ ] 先记录旧实现的失败表现。修复完成前以明确原因的严格预期失败记录，不允许整个套件模糊跳过；相应修复批次移除预期失败标记。
- [ ] 保存一组固定帧特征、采样时间线和对应区间，不依赖每次重新加载模型来检验 matcher。
- [ ] 建立小型真实素材开发集清单，覆盖短/长视频、4K、静态、高动态、变帧率；只有人工确认的片段关系才作为标签，不能凭文件名推断。
- [ ] 给基准增加纯读取源视频的安全边界；输出与临时媒体放隔离目录，不调用源文件自动隔离流程。
- [ ] 基线至少区分四种运行状态：无特征缓存、特征热缓存但强制重算视频对、断点复用、加入少量新视频。
- [ ] 记录 Python/依赖/设备、实际向量维度、实际模型输入尺寸、工作区差异摘要及运行配置。

**验收**：已有用例无意外回退；新用例能明确暴露旧行为；相同输入可复跑；原始视频及原缓存不被修改；基线结果可追溯到确切代码与配置。首次只建立工程基线，不发表准确率提升结论。

**交付**：测试用例、fixture 清单、基线 JSON、可复现命令及已知失败清单。

### B02：建立统一结果版本与缓存失效规则

**改动范围**：批处理断点签名、报告输出、桌面报告解析、缓存相关测试。

- [ ] 将模型权重标识、特征提取方式（如 pooler/projection）、数值精度、特征 schema 和评分版本纳入视频对结果身份。
- [ ] 使用两侧特征身份构建 pair 结果键，不能仅依靠文件大小/时间和部分界面参数。
- [ ] 区分帧特征缓存、匹配/对齐结果、片段与窗口派生结果。先落实正确失效规则，不在本批大改存储格式。
- [ ] 现代报告保留后端关系标签；仅对明确旧版本报告执行历史兼容推导。
- [ ] 补齐输入、评分、报告版本信息；旧格式仍能读取，未知版本不静默套用新语义。
- [ ] 更新模型实际输入尺寸和向量维度说明，暂不修改用户已有预设。

**验收**：改模型或 FP32/混合精度后不会恢复旧 pair 结果；改变纯展示设置不重提特征；同一现代报告在 Python/JSON/UI 中标签一致；老报告仍可查看；不同版本结果不能混用。

**回滚**：版本命名空间分离，保留旧缓存与报告；不能通过删除全部缓存强行“解决”兼容问题。

### B03：统一时序对齐，修复多候选与重复证据

**改动范围**：matcher、segmenter；必要时新增单一时序对齐模块及其测试。

- [ ] 先定义公共对齐结果：有效匹配点/轨迹、独立源目标帧数量、双方区间、拟合参数与残差、证据强度。
- [ ] 用多轨迹候选或受限路径搜索取代“所有 Top-K 点进入一条贪心轨迹”；保留多个真实复用片段。
- [ ] 以独立帧证据和时间跨度检验有效性，禁止重复候选仅凭点数通过。
- [ ] 对静态镜头允许受控多对一匹配，不能为了压低误报无条件强制一对一；证据不足时给出弱证据状态。
- [ ] 整体覆盖率与片段聚合使用同一套有效轨迹，移除两处互不一致的兼容规则。
- [ ] 将整体与片段的时序容差来源统一并版本化；默认先保持现有数值，避免同时改阈值。
- [ ] 明确限制路径数量、候选数量和计算复杂度，避免对长视频生成完整二维动态规划矩阵。

**验收**：固定多轨迹正例不再因增加第二条有效轨迹变为零覆盖；重复证据负例不再得到不合理全覆盖；原有稀疏、静态、乱序、轻微变速和多片段用例通过；双方有效区间可解释；性能无未说明的数量级恶化。

这里不要求“任何 Top-K 增加都必须单调增分”，而是保证已知有效轨迹不会被无关候选机械打断。精确率/召回率变化由正式标注集验证。

### B04：修复评分边界、关系规则和窗口口径

**改动范围**：覆盖率、关系判断、窗口统计、报告字段与对应展示。

- [ ] 时长可信时不再用抽帧数量覆盖时长判断；缺少时长的兼容行为单独定义。
- [ ] 末尾窗口裁到真实时长，分母采用窗口有效长度；正确分配跨窗口的采样时间单元。
- [ ] 正式覆盖指标只计入通过 B03 对齐的证据；如保留原始视觉窗口统计，使用不同字段名，防止误认为已验证覆盖。
- [ ] 输出绝对匹配秒数、双向覆盖率和证据质量，双向平均分仅作辅助。
- [ ] 区分“未筛入候选”“已比较不同”“证据不足”“比较失败”，不能把未比较当负例。
- [ ] 保留既有分类的兼容字段；两长视频局部短重叠如何进入结果筛选，先用匹配秒数表达，不在本批擅自增加破坏性的关系枚举。
- [ ] 更新评分版本并同步文档、报告解析与测试。

**验收**：10秒全匹配视频在60秒窗口配置下输出有效0–10秒窗口及100%覆盖；等时长不同采样密度不再单靠帧数被改判方向；整体、片段和窗口的差别有明确字段语义；短片段包含不会只因平均分低而不可见。

阶段1结束形成后续性能优化使用的**正确性基准版本**。后续性能批次与它比较，不能拿有已知缺陷的旧算法作为唯一结果标准。

**改动范围**：metrics、FAISS 配置、批处理计时、必要的 Tauri Python 启动参数。

- [ ] 清除“缓存预算值与实际 FAISS 状态不同步”的问题；在实际工作线程初始化时应用并读取线程设置。
- [ ] 统一视频对并发与 FAISS/PyTorch/OpenCV 内部线程的总预算，避免入口相互覆盖。
- [ ] 分别记录预检、模型加载、解码、几何预处理/pHash、嵌入、队列等待、缓存读写、摘要/候选、索引构建、对齐、派生统计及报告输出。
- [ ] 明确墙钟、累积工作时间、嵌套时间和等待时间，修复跨视频计数覆盖。
- [ ] 低频采样 CPU、RSS/峰值提交内存、I/O；GPU 支持时记录利用率及已分配/保留显存；不可获得的指标标记 unavailable。
- [ ] 对计时与资源采样本身做开关对照，避免采样开销成为新瓶颈。

**验收**：日志预算与实际执行线程一致；固定特征上的结果无语义变化；总墙钟覆盖报告写完；CPU/GPU 等待可区分；各指标标明口径与缺失值，不能将缺失写成0。

### B06：按字节控制内存与释放阶段资源

**改动范围**：解码批量、embedder 生命周期、ExactResourcePool、长视频向量写入。

- [ ] Decord 批大小按画面分辨率和预算计算，不固定64张原始帧。
- [ ] 资源池以两侧特征、索引和在途任务预计字节数做调度，保留引用计数、共享加载和成对租用。
- [ ] 区分“可控缓冲/索引预算”与“整个进程 RSS”：后者含原生解码器、模型及分配器，不能宣称绝对硬上限。
- [ ] 单对超过预算时走明确定义的低内存路径；尚不支持时明确报告资源不足并保留恢复状态，不能死等或静默突破预算。
- [ ] 提特征阶段结束且无后续消费者后释放模型；CUDA 清理只在阶段边界或真实 OOM 时执行。
- [ ] 减少 embedding_chunks 拼接副本；必要时分块落盘，但不与候选算法变更混合提交。
- [ ] 处理取消、异常退出、生产者未退出、池等待和文件句柄释放。

**验收**：固定采样帧和特征的结果一致；4K及长视频缓冲预算可验证；池内字节计数不超其约定上限；超大单对不死锁；取消/恢复、OOM回退及共享索引安全。进程峰值另作实测，不用理论公式代替。

### B07：优化冷缓存的解码与预处理

**改动范围**：frame_sampler、preprocess、必要的时间戳元数据。

- [ ] 根据 B05 证据决定优先处理解码、pHash还是几何变换，不盲目提高 frame_step。
- [ ] 先做不改变像素/采样结果的优化：共享裁剪坐标、减少原始帧拷贝、减少转换和对象创建。
- [ ] hash 与 CLIP 的插值方式不同，不能直接复用缩小图而声称无损。
- [ ] 缩小黑边检测图、稳定跨帧黑边、改变抽帧策略属于算法变化，分为独立实验，更新特征版本并测召回。
- [ ] 真实 PTS 适配作为单独子项：对变帧率与损坏时间戳做回退规则，不与纯速度变更混合。

**验收**：行为保持子项的采样索引/时间戳及特征满足固定一致性约定；算法变化子项通过独立精确度评价；冷缓存耗时改善对应实测瓶颈，不能靠减少覆盖范围冒充提速。

### B08：优化 GPU 批量、流水线与可选精度

**改动范围**：embedder、运行参数、设备指标；依赖可用且稳定的目标 GPU 环境。

- [ ] 先在 FP32 下对照实际批量8/16/32及队列容量，固定输入和采样。
- [ ] 以峰值显存和吞吐选择安全批量，保留OOM减半；桌面参数不能悄悄覆盖调度结果。
- [ ] 记录生产者/消费者等待，判断瓶颈是否真的在GPU。
- [ ] FP16/BF16分别作为非默认对照，校验向量漂移、阈值附近匹配翻转、最终标签/片段差异。
- [ ] 混合精度通过后才考虑提供用户模式；改变精度使用独立缓存身份。

**验收**：批量优化不改采样与识别语义；显存保留余量、OOM与取消正常；GPU指标由GPU实测。精度变化以预先冻结的准确率容忍度验收，不能仅看余弦均值接近1。

### B09：减少热缓存和增量任务的重复工作

**改动范围**：缓存摘要、候选选择入口、结果派生与恢复调度。

- [ ] 持久化每视频候选摘要和轻量元数据，使缓存审计不必加载完整向量。
- [ ] 校验摘要生成版本、模型、精度、抽帧/预处理配置和文件身份；失效时重建正确层级。
- [ ] 仅改窗口/展示设置时复用足够的匹配或对齐中间结果。若旧结果缺少必要证据，明确重算派生所需层级，不能凭240条展示样本重建完整结果。
- [ ] 新增视频时复用已有特征/摘要及已完成有效 pair 结果。
- [ ] 全局HNSW增量维护作为可选后续子项：先解决新增、删除、更新和墓碑/重建策略，再验证候选一致性及召回。
- [ ] 注意双向候选并集：新增视频可能改变旧视频候选排名；需要重新评估受影响选择，不能只做“新视频单向查询”便宣称与全量等价。

**验收**：未变更视频不重复提特征；未失效pair不重算；参数修改触发正确层级失效；完整重建与增量路径在约定模式下候选/结果一致，近似差异必须量化。新增/移除/改名/修改视频后无陈旧结果。

### B10：优化大库精确比较和结果存储

**改动范围**：匹配内循环、资源池任务排序、SQLite及报告读取。

- [ ] 按共享视频组织待比较任务，提高资源池命中；兼顾大任务公平性和取消延迟。
- [ ] 用紧凑数组承载候选点，完成筛选/对齐后再构建报告对象。
- [ ] 根据计时决定是否实现分块相似度计算同时维护双向Top-K；不能分配完整长视频相似度矩阵。
- [ ] 保持并列匹配的确定性策略，保守早停结果标记是否完整双向统计。
- [ ] SQLite复用连接与小批事务，明确可丢失的在途进度范围；恢复分页读，报告迭代生成。
- [ ] 以真实维度768、完整候选集合测试稠密与稀疏任务图，不只跑3对。

**验收**：固定特征结果一致或只有已约定数值误差；长视频峰值可控；崩溃后已提交结果保留；大报告不要求整表常驻；热缓存吞吐、加载次数与I/O有可复现变化。

### B11：候选片段二次验证与边界精化

**改动范围**：新增局部补采样/验证层，复用现有帧特征与对齐。

- [ ] 只在疑似片段及起止边界附近提高采样密度，不对全库无差别加密。
- [ ] 记录粗定位与精定位、有效证据、边界精度和验证成本。
- [ ] 处理短片段、跨切镜、重复片头/Logo、静态模板等案例。
- [ ] 内容身份复核作为证据层，不自动替代“语义相似”用途；两种模式明确区分。
- [ ] 精化阶段有限额，失败或资源不足时保留粗结果并标注未精化。

**验收**：双方区间IoU和起止误差改善；短片段召回与困难负例误报分别报告；额外耗时和资源符合预先定义的预算。

### B12：复杂变换与模型对照，最后重整预设

**改动范围**：可选变换/描述符实验、预设和说明文档。
